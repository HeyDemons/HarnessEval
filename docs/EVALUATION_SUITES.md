# Evaluation Suites

HarnessEval distinguishes two experiment scales without changing a harness,
prompt, tool contract, scorer, or task lifecycle:

- `light` is a versioned, materialized subset for development, ablations, and
  broad baseline-by-benchmark comparisons.
- `full` delegates case enumeration to the pinned benchmark release. It is the
  publication-scale setting and does not duplicate large datasets in this
  repository.

Resolve suite metadata or emit one frozen case list with:

```bash
harnesseval suite all --mode light
harnesseval suite gaia --mode light --json
harnesseval suite vitabench --mode light --ids-only
harnesseval suite all --mode full --json
```

Every result collection must record the suite mode, manifest SHA-256, benchmark
source revision, baseline revision, provider/model policy, and scorer version.
Light and full results must never be pooled into one aggregate.

## Frozen Light Design

| Benchmark | Cases | Stratification | Scoring scope |
| --- | ---: | --- | --- |
| GAIA 2023 | 60 | L1 10, L2 20, L3 30 | 56 locally scored; 4 L3 test cases require official submission |
| GDPval | 27 | 3 per each of 9 sectors; metadata-balanced complexity | Official rubrics; automated judging remains a proxy |
| VitaBench | 60 | 15 per delivery, OTA, in-store, and cross-domain | Native assertions and rubric evaluator |
| tau2/tau3 text | 30 | 10 per airline, retail, and telecom | Native state/action reward |
| BFCL V4 | 95 | 5 per each of 19 task categories | Native category-macro and pooled scoring |
| Terminal-Bench 2 | 20 | Public category, difficulty, and network metadata coverage | Native verifier after generic per-task adapter expansion |
| TRAJECT-Bench | held | No selection until replay endpoint validity is known | No score claim |
| SWE-bench Verified | held | Apple Silicon execution path under review | No score claim |

GAIA exposes only 26 public validation L3 cases. The light suite therefore uses
all 26 plus four hidden-answer test L3 cases to meet the requested 30-case L3
stratum. The four test cases are runnable but excluded from local accuracy and
rubric denominators until official submission scores exist.

`BFCL_v4_format_sensitivity.json` is an auxiliary ID map rather than a twentieth
task dataset. HarnessEval samples the 19 real task files and annotates whether
each selected case belongs to the format-sensitivity map.

## Selection Integrity

The committed manifests are generated by
`scripts/generate_light_suites.py`. Selection uses only pinned public metadata
and deterministic SHA-256 ranking. It does not inspect model answers, baseline
successes, runtime, token use, rubric scores, or historical run directories.

The VitaBench light suite is intentionally regenerated from the pinned official
registry. It does not reuse the historical result-informed VitaBench-60 list.
GDPval balances sector, occupation, deliverable type, reference count, and
rubric-item count without reading rubric text or model outputs.

To regenerate manifests on a maintainer checkout with the pinned data and local
VitaBench image:

```bash
/path/to/python-with-pyarrow scripts/generate_light_suites.py \
  --orch-root /path/to/orch
```

Regeneration is a reviewed dataset change. Existing paper runs retain their
recorded manifest hash and are not silently migrated.

## Execution Boundary

The suite layer selects cases; it does not rewrite them or introduce a generic
agent loop. A batch runner should call the same singleton `bridge-run` path for
each ID, preserving isolated artifacts, atomic results, resume, and native
scoring.

The Terminal-Bench 2 manifest is source-valid, but the current default catalog
still points to the `regex-log` task adapter. Running all 20 cases requires a
generic per-task adapter expansion. The manifest does not claim that work is
already complete.
